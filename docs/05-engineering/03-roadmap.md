# TURN P2P 施工路线与团队协作门槛（仍未批准施工）

> 更新：2026-11-18。**最新技术方向为 P2P**，不再以公网常驻专用游戏服务器为默认架构。所有真正的编码、安装插件、上传 GitHub、申请平台资格或部署服务仍需用户明确批准。

## 1. 已确认 / 未确认

**已确认**：Godot 4.7 + GDScript（补丁号待统一）、2～12 人、默认 8 人、全员准备后房主开始、每轮 15 秒、普通玩家掉线自动 PASS 且不立即淘汰、结束回房重新准备、P1 人机补位。

**仍待决**：房主型 P2P 或全员 Mesh、直连/打洞/Steam 平台/信令与 TURN 中继、房间码解析、房主看明文行动是否可接受、随机公平、Host 掉线、平台交付方式与付费资源。不能因为“P2P”三个字就默认这些技术能力已确定。

完整候选与决策门见 [P2P 架构 RFC](../02-architecture/03-p2p-architecture-options.md) 与 [决策登记簿](../00-product/02-open-decisions.md)。

## 2. Phase 0 · 理清条件与确定方案（当前阶段）

- 核对比赛最终提交环境：独立 Windows EXE、Steam、Web，团队成员与截止时间。
- 明确 P2P 是房主星形、全员 Mesh 还是其他；Host 断线时要中止还是迁移。
- 比较三条公网方案：ENet 端口映射、WebRTC + 信令/STUN/TURN、Steam/平台 P2P。不能提前安装插件。
- 把“D-04 房间码由谁解析”“D-05 15 秒如何与 Commit-Reveal 共存”“Host 是否能看其他玩家动作”写成可验收的协议。
- 检查项目已有能力、Godot 原生组件和可复用第三方方案，记录版本、许可证、兼容性。
- 确定后才提出 Phase 1 的具体变更文件与 Validation，先请用户明确批准。

**Validation（设计层）**：用户能清楚回答每项 D-03a～h 的备选方案、后果和依赖；没有未说明的服务器或平台账户前提。

## 3. Phase 1 · 纯规则与最小网络风险实验（批准后）

- GDScript 实现独立规则：发牌、手牌保留、PLAY/PASS、循环位移、淘汰、统计、终局。
- 测试所有边界：n=2..12、负位移、不同 card_id 同数字、牌值大于当前 n、重复提交。
- 用选定的 P2P 传输方式使两个 Godot 进程连接；在局域网成功后尽早跨公网测试。
- 若通过房间码加入，验证码映射到会话的全过程；若依赖平台中继，验证非开发机实际可用。
- 如果目标 P0 要求 Host 也不能偷看动作，单独测试 Commit-Reveal 的正确性及超时处理。

**Validation**：规则固定输入稳定、统计守恒；至少两台不同网络真实设备可连接。**没有通过公网前，不继续大规模制作 UI 美术。**

## 4. Phase 2 · P2P 房间/身份/15 秒回合

- 建房、邀请码/房间码、入房、人数上限 12、准备、房主开始、错误提示。
- 已选协调/权威模型负责生成公开起点及牌、收集动作、锁定与全员揭晓。
- 已确认 15 秒、提前全员确认、迟到 PASS、重复消息不重复结算。
- 普通玩家掉线保留席位，已提交动作保留/未确认 PASS；Host 离开按 D-03f 已批准的单独策略执行。
- 公共状态与秘密行动数据严格隔离；全部玩家一致显示结果。

**Validation**：2 人完整局→扩展 8/12 人；网络延迟/最后提交/断线测试；Host 与普通玩家掉线分开测。

## 5. Phase 3 · UI 与玩家体验

- Godot 原生 Control/Container + CanvasItem._draw，必要的 Tween/AnimationPlayer。
- 主菜单→创建/加入房间→准备→轮盘→15 秒选择→统一揭晓→结果→回房重新准备。
- 符合原文要求：轮盘扇区显示姓名与方形牌框，**中心空白、不显示扇区编号**。
- 2、8、12 人布局，1440×960、1180×820，累积手牌可读、不把按钮甩出窗口。
- 真人试玩 5～8 人，区分**主动 PASS**与**15 秒来不及而 PASS**；避免把时间压迫误判为玩法没有博弈。

**Validation**：操作可用、阅读准确、数据与网络状态一致、断线提示明确。

## 6. Phase 4 · 稳定性、第三方依赖与交付包

- 用最终 P2P 选型验证：公网不同网络设备完整一局、2/8/12 人、Host/成员掉线、房间失效/满房、非法动作与网络异常。
- 检查平台插件许可证、具体版本、导出打包依赖以及在非开发机上是否可启动。
- 明确外部服务的运行/费用/链接/账号要求（如果最终选择的网络路线确实需要）。
- 提供 Windows 客户端、建房入房操作说明及“选定 P2P 连接路径”使用说明；不再默认交付专用游戏服务器启动包。
- 原始 A01～A11 均需具备可复核测试证据，除非与用户约定了明确的业务需求变更。

**Validation**：完整真实公网对局和一致胜者；用户与队友不用开发机也能按说明运行。

## 8. 每次施工前必须进行复用审计

1. 项目现有场景/脚本/资源是否已有同类功能；
2. Godot 4.7 原生 API/节点能否直接复用；
3. 如需第三方，检查维护、许可证、实际兼容版本、导出平台与回退方案；
4. 自研部分必须说明为何无法直接复用；
5. 先交架构与修改计划，获得批准后实施；
6. 完成后按 **Summary + Validation** 提供真实测试结果，不将“写完代码”当成“验证完成”。

## 10. 2026-11-18 行动协议的先行设计门槛

已经**确认** 15 秒只用来选择与锁定承诺，之后可进入独立的揭晓验证阶段；在开始任何联网编码前，应先完成 [Commit–Reveal RFC v0.2](../03-network/04-commit-reveal-rfc.md) 的审批：

1. FREEZE 的最大等待时间、完整 manifest ACK 的最小认证强度。
2. REVEAL 的最大等待时间，是否所有玩家自动揭晓及超时重试。
3. **D-03j 最关键**：有承诺但无法揭晓时，选 N1 继续按 PASS / N2 异常终止 / N3 可信托管。这会影响已批准 D-06 的“已确认合法行动保留”，不可默默覆盖。
4. Host 是否需要可验证的公开随机骰娘，行动哈希并不保证随机公平。
5. D-03k 要防到哪一级恶意房主：不提前知道 / 共识名单不可伪造 / 保证中途掉线也能自动揭晓。

参数草案 15 秒 COMMIT + 最多 2 秒 FREEZE + 最多 5 秒 REVEAL 仍为**实验建议、尚未定案**。纯规则与 UI 模块应继续独立于传输方案。本轮不开始任何实验或功能施工。

## 11. 2026-11-18 最小 Demo 优先级调整

用户希望以 GameJam 效率为优先，不提前构建防恶意 Host 的签名网络、全员共识、托管服务、主机迁移或过度复杂异常恢复。为避免长期停留在 RFC 评审阶段，**当前已具备最小 Demo 的设计条件**，建议先走 Godot 4.7 原生 ENet + Host-Client + 15 秒 Commit–Reveal 的本机/局域网正常流程，逐步验证异网连接。完整代码边界、验收和明确未实现项见 [最小 Demo 计划](05-minimal-demo-plan.md)。

旧 RFC 的 N1/N2/N3、冻结签名 ACK、Escrow 与完整公网 NAT 策略保留为后续待决，不应阻止正常流程的最小验证。**原 P0 仍需真实跨公网、多设备和 12 人上限验收；Demo 不得冒充正式完成。** 本轮只修改文档，是否正式编码等待用户明确下令。
