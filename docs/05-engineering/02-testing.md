## 1. 三层测试

### L1 · 规则单元测试（尽早、自动化）

推荐先在纯 GDScript 规则层编写可重复的测试。若引入第三方测试框架，应先审批并且 GUT/GdUnit4 二选一。

| 测试组 | 关键断言 |
| --- | --- |
| 发牌 | n 人新增恰好 n 张牌、范围 `1..n`、独立抽取允许重复 |
| 手牌保留 | 本轮未用旧牌不变；牌值可以 > 当前 n |
| 随机指向 | 服务端从当前存活列表选，使用固定 seed 可重现；公平性可另做统计试验 |
| 位移求和 | 正负、多位数、完全抵消、全员 PASS |
| 环绕公式 | 负位移、超 n 位移、n 倍数移动为 0 |
| 身份/索引 | 淘汰后相对顺序保持、位置重新编号、player_id 不变化 |
| 消耗/弃牌 | PLAY 只消费一张指定 card_id；淘汰者剩余牌全部弃置且不被继承 |
| 重复数字 | 同数字不同 card_id 正确保留和删除 |
| 终局 | 剩一人后不发牌、不新开回合，胜者稳定 |
| 统计恒等式 | 每数字和总数 `issued = played + eliminated + held` |

### L2 · 网络状态机和多实例集成

- 两客户端进入同房，分别看到**自己的**「你」标识，但所有人牌和轮盘顺序一致。
- 未公开前，检查实际到达客户端的数据包/解码消息结构，确认**没有其他人的行动内容**；只藏 UI 不算通过。
- 同时提交最后一人动作与到期定时器：整个回合只揭晓一次、淘汰一次、轮次递增一次。
- 上一轮 RPC、重复请求、伪造 player_id、非本人 card_id：服务端拒绝且逻辑状态不变。
- 双房同时运行：一个房间无权访问/影响另一房间；事件只发对应成员。
- 一人掉线（确认前/确认后）其余玩家能继续，默认 PASS 与保留行动分别正确。
- 全部断开房间释放；对局结束再开始清除旧统计、牌和锁定集合。
- 时间流逝以服务端为准；断网恢复/重新连接**不承诺找回席位**（首版）。

### L3 · 真机、公网、布局与构建

- 客户端在 Windows 非开发机运行，服务器在明确的公网地址。
- **两台不同网络设备**完整建房、发牌、出牌、淘汰、胜负；记录时间与连接方式。
- 2、8、12 人规模、多轮牌数积累与 1440×960、1180×820 UI 检查。
- 导出后中文可读、服务器地址可配置、连接失败可重试。
- 测试服务器停止或端口不可达时，不会永久卡 UI 或导致错误的胜负。

## 3. 用例细化：关键竞态

### Case RACE-01 · 超时与最后一份动作一起到

- Given：房间处于 CHOOSING，有 1 人尚未确认。
- When：收到其动作的同一处理周期，服务器到期事件也执行。
- Then：两条路径只能有一条从 CHOOSING 成功切到 REVEALING；**恰好一次**出牌锁定、揭晓和淘汰；另一条处理无副作用。

### Case ID-02 · 两张同数字不同身份的牌

- Given：玩家持有 card_5 与 card_10，都为数值 3。
- When：打出 card_10。
- Then：card_10 记入 PLAYED、card_5 仍 HELD；界面剩余牌卡对应正确 ID，统计守恒。

### Case SECRET-03 · A 已提交，B 还没确认

- Given：A、B 在同一房间，A 提交某张牌 +。
- When：B 收到 `locked_count_changed`/`public_snapshot`。
- Then：B 只知道确认数量和公开手牌；不知道 A 选择了牌、符号，甚至不能从消息字段推断；统一揭晓前不会有 `round_revealed`。

### Case ROOM-04 · 两房间同时揭晓

- Given：房间 A 与 B 有不同玩家/回合。
- When：A 所有人确认触发揭晓。
- Then：B 无 A 的事件、无错误淘汰、无统计改变；B 仍保持自己的 CHOOSING。

### Case COUNT-05 · 自己出牌后被本轮淘汰

- Given：目标玩家本轮 PLAY，手中仍有两张其他牌。
- When：本轮指向该玩家。
- Then：打出的只计 PLAYED，一共两张剩余牌计 ELIMINATED；不能重复计数，其他玩家 HELD 不变。

## 4. 记录格式

每条验收记录至少包含：
- 构建/Commit ID，Godot 补丁版本，服务端部署版本；
- 用例 ID，人数，参与者网络类型，开始与结束时间；
- 具体操作步骤、预期、实际结果、失败日志/截图位置；
- 结论：通过/失败/阻塞；缺陷 ID；复测日期。

**当前所有测试都应标为「未执行」**，因为没有游戏脚本、服务端或客户端可以运行。

## 8. 2026-11-18 Commit–Reveal RFC v0.2 测试追加（NOT RUN）

用户已确定“15 秒仅供选择和锁定，之后单独揭晓验证”，不等于 FREEZE/REVEAL 时长已批准。

| 编号 | 专项验证 | 预期 |
| --- | --- | --- |
| CR-01 | 2/8/12 人均提交 hash（包括 Host 和 PASS） | 提前全部确认时直接冻结，无明文在 15 秒期间泄露 |
| CR-02 | 尝试枚举公开手牌的所有行动猜测承诺 | 32 字节高熵 nonce 令实际行动无法被低成本穷举恢复 |
| CR-03 | 提交两种 hash、过期 round、错误 player_id、重复 commit | 首次合法 commit 锁定，后续改变拒绝，重发幂等 |
| CR-04 | Host 没有合法自身 commit 就要求 REVEAL | 客户端拒绝，不能先揭晓再锁 Host |
| CR-05 | Host 向不同客户端发送不同承诺名单 | 至少能发现 manifest_hash 分歧；若要求抗恶意 Host 的完整防分叉，另测签名/共同见证 |
| CR-06 | 恰好在 15 秒截止和最后提交同时触发 | COMMIT_OPEN → FREEZE 只执行一次 |
| CR-07 | 玩家 15 秒未提交 hash | AUTO_PASS，不能消耗手牌 |
| CR-08 | 玩家已提交 hash 但揭晓前断线 | **D-03j 待决**，禁止擅自按“已确认行动执行”或“自动 PASS”伪造结果 |
| CR-09 | Reveal 改动作/错 nonce/非本人牌/无效 sign | 校验失败，不能计入合法 PLAY |
| CR-10 | Host 只转发一部分揭晓、网络顺序不同 | 各客户端验证完整集合，不能在状态不同步时分别给出胜者 |
| CR-11 | Host 恶意停服 | 不承诺完全防拒绝服务，按 D-03f 提示终止；不得展示虚假完成局 |
| CR-12 | Host 操纵发牌种子 | Action Commit–Reveal 无法检测，须另评 DiceService 随机公平级别 |

对应协议与缺席揭晓的 N1/N2/N3 权衡见 [Commit–Reveal RFC](../03-network/04-commit-reveal-rfc.md)。当前全部未执行、不代表测试通过。

## 9. LIFE-01 初始生命可调整的验收矩阵（2026-11-18）

- **初始生命=1**：保持原始“一命即淘汰”的规则和 12 人 11 回合、77 张发牌的原测试结果。
- **初始生命=3**：2 人连续命中同一玩家 3 次，生命 3→2→1→0；前两次不淘汰、不弃置未使用牌、不缩盘，第三次归零淘汰；胜者一致。
- **初始生命=5**：12 人逻辑压力样例连续命中最先存活的玩家，55 回合、385 张发牌，全部结算保持牌数守恒；不是 12 人 GUI/网络压力通过。
- **房间设置同步**：Host 的 SpinBox 改为 3，Client 显示同一个 3，Client 不能更改；开始后锁定；终局回房保持初始生命配置供下一局再次选择。
- **界面**：轮盘和完整手牌区显示每名存活玩家当前生命；命中但未归零显示扣血，归零才显示淘汰。
- 所有截图、运行日志和已知限制见 [实际 Demo Validation](06-demo-validation.md)。

旧版 A02/A03/统计等依赖“每轮必淘汰”的测试描述只适用于初始生命为1的情况，见 [生命规则](../01-gameplay/03-initial-lives.md)。
