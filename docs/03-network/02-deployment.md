# TURN：P2P 网络交付、连接方式与运行约束

> 状态：2026-11-18 **P2P 方向已确认，具体连接服务尚待讨论**。旧版“固定公网 Headless 专用游戏服务器”的部署方案不再是默认施工路线。  
> 依然需要：至少两台处于不同网络的设备通过真正互联网连接，完成同一局且胜负一致。局域网/同机多开不算最终交付。

## 1. 现在不应该直接买服务器

P2P 代表游戏实际会话由玩家设备承担（如果选房主型 P2P，房主本机执行比赛规则）。是否需要额外服务，取决于连接途径：

- **纯直连 ENet**：不需要自建专用游戏服务器，也可不部署其他服务；但房主可能要有公网可达地址并映射 UDP 端口，无法保证所有校园网/运营商 NAT/手机热点能连。
- **WebRTC P2P**：通常有信令与 STUN；直连失败需要 TURN 中继兜底。**信令/中继是外部网络服务，但游戏结算仍在玩家设备**。Windows 原生 Godot 需要 WebRTC GDExtension，先核对具体版本/许可证。
- **Steam 等平台 P2P**：可能由平台处理 Lobby、身份与中继，无需自建这些服务；但使用权限、平台账号、分发方式、插件维护/兼容性要先确认。
- **WebSocket 本身**：只是通信协议。两端都连接一台 WebSocket 服务器并在那儿运行所有规则时，属于客户端-服务器，不是用户要求的 P2P；它可以只用于 WebRTC 信令。

详见 [P2P 连接能力比较](03-p2p-connectivity-options.md)。

## 2. 本轮 P0 交付需要回答的实际问题

| 问题 | 为什么现在不能省略 |
| --- | --- |
| 短房间码由谁分配与解析？ | D-04 已确认房间码，裸 ENet 直连不会自动提供码→Host 的查找服务 |
| 房主网络是否需要开端口？ | 直连对不同 NAT 条件不保证成功 |
| 直连失败怎么办？ | 提示错误 / 引入平台中继或 TURN，关系到“不同网络必须可玩” |
| 玩家是否必须登陆平台？ | 会直接影响 GameJam Windows 独立客户端的可用性 |
| Host 退出会怎样？ | D-06 只明确非协调者掉线的 PASS；Host 断开可能导致对局整体结束 |
| 动作是否必须对 Host 保密？ | Host 接收明文则会提前获知其他人选择，需决定是否采用哈希承诺 |
| 是否支付服务费用？ | 取决于是否部署信令、TURN、中继或者使用有条件的平台服务 |

## 3. 候选连通方案的验收顺序（在选型并获批准后）

1. 同机多开最小协议冒烟，确保节点/消息格式正确。
2. 同一个局域网 Host/Client 入房，验证房间/准备/15 秒回合。
3. 不同 NAT 的两台 Windows 设备，一台校园网、一台家庭宽带或移动热点，实测直连/中继。
4. 12 人容量与 2/8/12 人轮盘布局；房主与非房主分别尝试断网。
5. 密码/房间码错误、房间满员、过期、重复提交、网络短暂中断、Host 失效均有明确 UI 响应。
6. 第三方 P2P 平台要在最终可交付的**非开发机客户端**中实测，而不只是编辑器里的演示。
7. 通过 A01～A11 后才能声称 P0 在线交付完成。

## 4. 当前已批准业务规则，不因 P2P 被更改

- Godot 4.7 + GDScript，具体团队补丁版待统一。
- 支持 2～12 人，默认 8 人。
- 房主建房，全员准备且至少 2 人才能开始。
- 每轮 15 秒，所有存活者确认可提前揭晓，未确认者超时 PASS。
- 一般成员掉线保留席位与已锁定行动；未确认和以后轮次 PASS；**Host 退出另外决策**。
- 对局结束返回房间、重新准备；进行中拒绝新玩家加入。
- 人机补位 P1。基础玩法、明牌保留、加减、淘汰、统计不变量保持原需求。
- 部署/插件/Steamworks 账号/费用均尚未批准，不进行任何申请或安装。

## 5. 必须让队友知道的限制

- 不要默认一个短码就可以公网连接，除非已经确定并实现短码的**发现与连接**过程。
- 不要默认 `ENetMultiplayerPeer.create_mesh` 或 WebRTC `create_mesh` 自动完成所有玩家的 NAT 穿透与随机共识。
- 不要把“非房主断线自动 PASS”误写成“房主断线也能自动继续”。
- 不要把“客户端 UI 看不到对方出牌”误当作“房主无法读取他人的明文秘密动作”。
- 若选择 Steam 等外部服务，验证其**实际接入门槛和使用条款**后再把它视为解决方案；平台中继不等于无需任何服务。
