# TURN：P2P 会话协议设计（拓扑/传输待决）

> 状态：2026-11-18 RFC。已确认使用 **P2P**，但房主型/全网状、是否需要外部信令与具体网络库仍未批准。本文区分**业务契约**与**候选实现**，不代表代码已存在。
>
> 已确认的业务行为：2～12 人（默认 8）、凭码建房/入房、至少 2 人且全员准备后房主开始、15 秒内同时秘密决策、全员提前完成即可揭晓、掉线普通玩家保留席位/未确认 PASS、结束回房再准备、Bot 为 P1。

## 1. 不可混淆的两类决定

**网络拓扑**（如何相连）与**游戏裁决**（谁判断正确）是不同问题。
- Host-Client P2P：房主客户端可以是唯一的游戏逻辑权威，其他玩家对它发送指令；这是候选 A。
- Full Mesh：所有玩家互联，但谁负责统一时钟、随机与回合收尾仍需确定；这是候选 B。
- Host-Client + Commit-Reveal：房主协调，但不能提前看对手真实选择，协议需新增承诺和揭晓两阶段；这是候选 C。
- 原 v0.1 的专用“公网权威服务器”是被 P2P 最新要求取代的旧推荐，不能继续作为正式实施前提。

更多比较参见 [P2P 架构设计 RFC](../02-architecture/03-p2p-architecture-options.md)。

## 2. 建房、发现与身份

- 确认产品流程：建房→返回房间码→其他人输码加入→成员看到 a、b、c… 和“你”→准备→房主开始。
- **技术未决**：短房间码必须可映射到网络会话。直接分享 IP:端口、平台 Lobby ID 或自建轻量发现服务是不同实现，不能默认房间码由 ENet 自己产生。
- 业务逻辑记录 `room_id`、`room_code`（用户可见）、`match_id`、`player_id`（一局内稳定）和与连接绑定的 `peer_id`。网络连接拥有者不可伪造另一个 player_id 发出行动。
- 2～12 人；满房、第 13 人、已经开始、码错误均应给出明确错误。房主在房间阶段离开时可将房主权限转交其余在线成员；对局中 Host 离开还需要独立方案。
- P2P 后不一定有“同一台中央服务器上多个房间”的 RoomManager。若有平台 Lobby 服务，它负责房间发现；游戏规则仍留在玩家设备。

## 3. 建议的传输无关业务消息

| 方向 | 消息 | 主要内容 |
| --- | --- | --- |
| 加入者 → 房主/协调端 | `JOIN_REQUEST` | 会话/邀请码、协议版本、连接身份 |
| 协调端 → 已授权成员 | `ROOM_SNAPSHOT` | room_id、房间码、成员、准备、房主、容量 |
| 成员 → 协调端 | `READY` | ready 状态 |
| 房主 → 协调端 | `START_MATCH` | 仅房主，>=2 人且所有成员准备 |
| 协调端 → 成员 | `ROUND_START` | match_id、round_id、alive_order、明牌、初始指向、15 秒截止 |
| 玩家 → 协调端 | `ACTION_SUBMIT` | 简单方案：PASS 或本人的 card_id 与 +/−（**房主能读明文**） |
| 玩家 → 协调端 | `ACTION_COMMIT` / `ACTION_REVEAL` | 候选公平方案：承诺哈希 → 后续动作+随机盐揭晓 |
| 协调端 → 成员 | `LOCKED_COUNT` | 已确认人数；不得泄露明牌之外的秘密选择 |
| 协调端 → 成员 | `ROUND_REVEALED` | 揭晓全部动作/已验证承诺、合计位移 |
| 协调端 → 成员 | `ROUND_RESULT` | 唯一淘汰者、弃牌、完整牌数统计、胜负/下轮 |
| 成员 → 协调端 | `REQUEST_PUBLIC_SNAPSHOT` | 已知状态版本；只可获取公开字段 |
| 协调端 → 成员 | `ERROR`、`MATCH_END` | 非法输入/断连与结果、回房状态 |

- `room_id/match_id/round_id/sequence` 用于阻止跨房和跨局过期操作；`request_id` 用于幂等日志。身份来自已经验证的连接，不是客户端自报。
- 公开数据应以明确字段白名单生成，不能把保存有 `pending_actions` 的内部状态对象原样发给客户端。
- RPC、消息序列化与加密具体技术由 D-03b 决定。Godot 的 MultiplayerAPI 与 RPC 是 **可以复用的候选**，不是当前唯一已批准方案。

## 4. 15 秒回合与秘密动作的两种协议（暂不内定）

**已确认的用户体验**：从本轮开始出现 15 秒决策期；所有存活者完成确认可提前结束。未确认自动 PASS，已确认不可更改。不同玩家不应在统一揭晓前收到其他人的选择。

### 路线 S：向 Host 直接发送明文最终行动

- 简单：Host 接收 `ACTION_SUBMIT`，确认卡牌属于该玩家，锁定一次；全员确认/到期后公开并结算。
- 其他非 Host 客户端在揭晓前不会收到动作，**但 Host 本人可以阅读其他人的行动**；原文“秘密决策”是否容许房主例外，需要用户明确决定。
- 截止时刻以 Host 的单调时钟为准；本地客户端倒计时仅是展示。

### 路线 C：Commit → Reveal（更加公平但更复杂）

1. 玩家在 15 秒内生成动作与随机盐，只发送 `SHA256(确定编码(action, match_id, round_id, player_id, nonce))`。
2. 提交期结束后进入独立揭晓阶段，玩家发送 action + nonce。
3. 协调端逐个验证 SHA256，构建可复核的完整动作集合并结算。
4. 明确超时无 Commit = PASS；**有 Commit 但不 Reveal** 的后果、Reveal 额外截止时间、断线时已承诺动作怎样处理必须另行讨论。
5. Hash 承诺并不自动解决发牌随机公平、房主隐藏消息或 Host 迁移等问题。

**2026-11-18 更新：用户已同意 15 秒只用于决策与锁定，之后允许单独的短暂揭晓验证阶段。** 额外时长、冻结名单、缺席揭晓与恶意 Host 处理仍待审批；详见 [Commit–Reveal RFC v0.2](04-commit-reveal-rfc.md)。哈希不能证明完全无作弊。

## 5. 结算和统计的确定性协议

本轮存活 n 人、起点索引 s、锁定加减总和 delta，则 `target=((s+delta)%n+n)%n`，唯一目标出局。
- 重复 card_id、已出牌、非本人牌、错回合和已确认重发应无副作用。
- 出局者本轮打过牌的先计 PLAYED，其余 Held 再计 ELIMINATED；别人不继承。
- `已发 = 已出 + 淘汰弃 + 剩余` 在结算完成后按牌值和总量成立。
- 本轮最终动作、统计和结果必须有唯一可验证版本；Host 型由 Host 发布权威事件，Mesh 型必须额外实现一致性/共识。
- 只有一人存活时结束，不再发牌；结束后回房间全员重新准备，新 match_id。

## 6. 掉线的两类情形

- **普通参与者**（已确认 D-06）：本轮已确认动作保留；未确认 PASS，后续轮次 PASS；不能立刻因为掉线淘汰。下轮仍计入存活轮盘，直到正常出局。
- **Host/协调者掉线**（**未决 D-03f**）：没有备用协调者时，剩余节点可能拿不到下一回合、随机牌、时钟与统一结果。候选：立即中止并通知、迁移 Host、部分平台会话恢复。**不可悄悄套用 D-06**。
- 在 Mesh 模式下，任何成员断开时其余成员是否仍能达成共识也需要额外的协议与验收。

## 7. 过期、重试和异常保护

- 同轮动作只锁定一次；最后一个动作与 15 秒超时竞态只能触发**一次**结算。
- 使用 `match_id`、`round_id` 和版本过滤旧请求、重复包和旧快照。
- 传输断开必须有 UI 提示，不能显示虚假的“已经加入房间/已经确认”。
- 若采用 Godot RPC，双方 NodePath 和 RPC 声明一致，服务端/Host 入站检查 sender peer 和阶段；如选 Mesh，需要按各方角色重审 RPC 权限。
- 任何模式都不得在未揭晓前广播真实动作给不该知道的玩家。

## 8. 测试计划（尚未执行）

1. 2/8/12 人规则、牌归属、负位移、重复与统计守恒。
2. P2P 局域网和**两种不同公网网络**完整对局；不能仅本机多开。
3. 假码、满房、未准备、非房主强开局、对局中加入拒绝。
4. 15 秒/提前确认/无人确认/临界时间/已确认后掉线/未确认掉线。
5. 未揭晓前所有非授权客户端收到的数据审计；若要求包括 Host 不可获明文，则必须测试 Commit-Reveal。
6. Host 离开时按最终 D-03f 决议处理，不能虚构继续游戏能力。
7. 每次更换具体 P2P 传输插件后重跑身份、保密和网络异常测试。

## 10. Commit–Reveal v0.2 评审结论（覆盖本文件旧明文提交候选）

用户已确认房主也不得在选择期提前看到他人的明文选择，因此本文件的“直接给 Host 明文的路线 S”**不符合当前保密需求，只保留历史对比**。当前进一步设计的协议由 [RFC v0.2](04-commit-reveal-rfc.md) 给出：

- 15 秒期间每名玩家（包括 Host）只提交带 32 字节随机盐的 SHA-256 承诺哈希，PASS 也需承诺；Host 不收真实 card_id/sign/nonce。
- 15 秒到期或所有存活者完成承诺 → 冻结公共承诺名单（含 Host 的承诺和无提交者的 AUTO_PASS）→ 客户端确认同一名单 → 独立 REVEAL 自动提交原行动和盐 → 每端校验后再结算。
- “冻结最多 2 秒、揭晓最多 5 秒”只作为**建议实验参数**，尚未获得批准。
- 必须严格区分 **未提交承诺**（按已确认超时规则 AUTO_PASS）与 **已提交承诺但未揭晓**（**D-03j 待决，不可擅自改判 PASS**）。
- Host 星形拓扑下他可能选择性隐藏消息、发送不同名单、停止服务；普通 SHA-256 不能保证这些异常都自动恢复。若要求更强公平，需要签名/共同见证或可信动作托管。
- Godot 的 Crypto 与 HashingContext 已有需要的原生基础能力；本轮没有实现/安装任何代码或服务。
