## C. P2P 必须单独拆开的 8 项技术决策（均未批准具体方案）

> C 至 H 节对应 2026-11-18 玩家房主原型的评审记录。

| ID | 需要决策的事项 | 候选方案与关键取舍 |
| --- | --- | --- |
| D-03a | **拓扑** | 房主型 Host-Client P2P（连接数少、简单）/ 全员 Mesh（连接多、状态共识复杂） |
| D-03b | **底层公网通信** | ENet 直接连接+端口映射 / WebRTC+原生插件+信令/ICE / Steam 等平台 P2P / 其他 |
| D-03c | **房间码/发现** | 平台 Lobby 或邀请码 / 轻量信令发现服务 / 连接信息编码（不是普通短码，涉及 D-04 体验变更） |
| D-03d | **房主不得提前知道他人的行动** | **保密目标已确认**；Commit-Reveal 是当前评审方案，是否需要更强的可信托管仍待决定 |
| D-03e | **随机数公平性** | 房主生成牌和起点 / 多方联合随机或可验证随机 |
| D-03f | **Host 断线** | 中止对局并提示 / 迁移 Host 并继续 / 其他。**不能与 D-06 普通成员自动 PASS 混淆** |
| D-03g | **可接受的外部服务** | 零自建常驻服务（允许用户端口配置）/ 可使用 Steam 等第三方平台 / 可部署轻量信令/TURN 中继 |
| D-03h | **平台/账号条件** | 独立 Windows EXE 不登录 / 允许 Steam 账号和 Steamworks / 要求浏览器或多端 |

**P2P 是已确认的拓扑方向，但“完全 Mesh、没有任何服务器/平台、所有人无端口配置一键跨公网”并不是自动附赠的功能。** 详见 [整体 P2P 架构 RFC](../02-architecture/03-p2p-architecture-options.md) 和 [公网连通技术比较](../03-network/03-p2p-connectivity-options.md)。

## D. 与原文冲突及保持不变的部分

- **有冲突且已覆盖**：v0.1 §7.1 “建议公网权威服务端”、NET-01 “统一服务地址”、P0 客户端+专用服务端启动等措辞。这些是旧实现设想，最新以 P2P 为准；但仍必须在 P2P 下满足原本的公网真实可玩目标。
- **必须保持**：2～12 人、每轮存活者各一张明牌、旧牌不变、同时秘密选择、统一公开、循环位移/一轮一淘汰、统计守恒、不能重复结算。
- **业务已更新**：原文建议回合 20 秒已被用户批准的 **15 秒**取代；房主准备与开局、普通成员掉线策略、结束回房、人机 P1 均已批准。
- **新发现的冲突**：房主型 P2P 在 Host 收集**明文行动**时，Host 本人可提前得知别人出牌；原文的秘密选择目标需要独立决策；Host 离线与 D-06 的一般断线处理也必须分开。
- **需要确认的边界**：若要求短房间码直接找到全网房主，必须明确发现/信令服务或平台 Lobby 机制；单纯 ENet 不自带此服务。

## E. 后续评审顺序（只讨论，不施工）

1. 优先讨论 **D-03a / D-03g**：房主型还是 Mesh？能不能接受平台/轻量网络服务？
2. 再讨论 **D-03b / D-03c / D-03h**：实际网络技术、房间码来源、账号和发行平台。
3. 再讨论 **D-03d / D-03e / D-03f**：房主公平性、随机、Host 掉线后如何继续。
4. 完成以上决策后，用小规模网络实验验证跨网连接，再评审是否开始功能编写。

## F. 开发质量门槛

每次新增功能前查项目内现有实现、Godot 4.7 原生 API/节点、成熟插件版本与许可证，优先复用，必要定制写清理由、影响文件、测试和回退方式。每次阶段交付用 **Summary + Validation**，未经用户批准不安装依赖、不修改游戏功能代码、不购买部署资源。

## G. 2026-11-18 进一步约束：常见房主型 P2P 优先研究，不锁传输

本轮用户明确提出以下偏好及要求（不要误判为全部技术选型已批准）：

| 事项 | 最新状态 | 含义与未解决部分 |
| --- | --- | --- |
| D-03a 拓扑 | **优先研究房主型 Host-Client**，不优先 12 人全员 Mesh | 房主也是玩家；Host 可以兼任逻辑协调者，但不意味着 Host 可偷看动作 |
| D-03b 网络技术 | **Steam 明确排除**；ENet、WebRTC 等仍需比较 | ENet 原生直连常遇到 NAT/端口映射；WebRTC 需要信令、原生插件及视情况使用 TURN 中继 |
| D-03c 房间码 | **暂未决定**，要求进一步解释 | 若要短码找到世界各地的房主，通常需要平台或轻量发现服务；仅生成本地随机码无法跨网查找 |
| D-03d 行动秘密 | **房主也不能在决策期间提前看其他玩家的明文行动** | Host-Client 需要 Hash Commit-Reveal，或者独立可信服务托管秘密提交；揭晓顺序与超时仍需定义 |
| D-03e 随机 | 希望采用“**骰娘式**”向所有玩家共同展示随机结果 | “公开可见”与“防止 Host 操纵随机/重掷”是两个等级；随机机制托管方与可验证性仍待决定 |
| D-03f Host 掉线 | **倾向首版 Host 断线即终止房间，不做迁移** | 需要最终确认；D-06 的普通玩家断线自动 PASS 不适用于 Host 进程关闭 |
| D-03g 基础设施 | **必要时可以接受轻量服务**，但不预设必须部署 | 发现/信令与 TURN 中继是不同职责；不能把发现服务误认为自动 NAT 穿透 |
| D-03h 发行 | **独立 Windows EXE**，不依赖 Steam | 插件与网络依赖需随打包完成，不能要求 Steam 账号 |

### 当前推荐的评审顺序

1. 先评审 Host-Client 的**提交承诺/揭晓**：15 秒怎样划分？缺席揭晓如何处理？Host 能否单方中止？
2. 再评审**公网连接及短房间码**：ENet 直连、WebRTC + Signaling/STUN/TURN，必要时轻量中继。跨网实测不能省略。
3. 再决定**骰娘式随机**：只做公开可见还是要求无单方操控。
4. 完成各项决策后明确批准最小网络实验；**尚未批准插件安装、联网代码或部署**。

## H. 2026-11-18 行动保密协议的新决定与待决项

用户本次**已确认**：**15 秒只用于选择和锁定行动；之后允许短暂、独立的 Reveal 验证阶段。** 房主作为玩家同样不得在选择期获得其他人的明文行动。但用户尚未批准承诺名单协议、超时秒数、未揭晓处罚或者上线实现。

- **D-03i（待决）**：Commit 15 秒已确定；FREEZE 建议最多 2 秒、REVEAL 建议最多 5 秒是待评审的参数，须真实网络实测。
- **D-03j（待决，影响既有 D-06）**：若玩家已经提交 hash 承诺，却在揭晓前掉线，SHA-256 无法还原原行动。选项 N1：未揭晓自动 PASS（易遭战略性不揭晓利用，并冲突“已确认行动保留”）；N2：异常暂停/终止本轮或整场（可能被恶意卡局）；N3：可信轻量 Escrow 在截止时自动公布动作（需额外在线服务与信任）。
- **D-03k（待决）**：Host 对手选择保密的强度。K1：承诺+共同名单+终局核验；K2：签名 ACK 或见证服务防 Host 伪造/分叉承诺名单；K3：可信托管保障掉线已确认行动自动揭晓。
- **D-03e（待决）**：DiceService 仅公布每轮随机结果，还是要求多人种子/可信随机服务防止房主选择性重掷。行动 Commit–Reveal 不自动保证发牌随机公平。

本次详细依据与异常矩阵见 [Commit–Reveal RFC v0.2](../03-network/04-commit-reveal-rfc.md)。**不要把“已承诺”与“已经验证并执行的合法出牌”当成同一件事。**

## I. D-22 可调整初始生命（2026-11-18）

- **已确认的需求**：在最小 Demo 增加初始生命可调整。工程初始值采用每人相同、**房主大厅设置、默认 1、可选整数 1～5**。这些数值边界为方便试玩的实现参数，之后可根据反馈变化。
- **Demo 具体规则**：每轮轮盘命中者扣 1 生命；生命大于 0 保留席位和未打手牌，生命为 0 才淘汰并弃牌；最终只剩一人获胜。默认 1 生命恢复此前玩法。
- 影响：原“一轮一淘汰”和“最多 11 轮/77 张（12 人）”在多生命时**不再适用**。长牌列显示与节奏需重新测试。
- 当前工程已使用原生 SpinBox 及已有消息同步，没有增加第三方组件。见 [生命规则](../01-gameplay/03-initial-lives.md) 和 [测试记录](../05-engineering/06-demo-validation.md)。
