# TURN 规则规格 v0.3（初始生命可调，其他基本玩法沿用 v0.1）

> **技术更新（2026-11-18）**：规则不变，但联网方向已确认为 P2P。旧稿“服务端”一词仅表示统一裁决职责，不表示另有固定公网专用服务器；Host 还是 Mesh 尚未选定。

> 文档状态：待评审。标记为「实现定义」的内容用于消除歧义，不改变已确认玩法。  
> 不引入暗牌、特殊牌、继承牌或额外获胜方式。

## 1. 基本量与身份

- 初始玩家数 `N0∈[2,12]`，只有玩家生命降至 0 并淘汰时存活人数 `n` 才递减。
- `player_id`：同一局稳定的内部身份，淘汰、重排后**不改变**。
- `display_name`：a、b、c……，初次进入房间分配后保持稳定；「你」由客户端根据自己的 peer 映射产生。
- `wheel_index`：**当前轮盘位置**，本轮按 `1..n` 顺时针排列，淘汰后会重新编号。
- `card_id`：同一局唯一且不可重用的牌身份。牌值相同的两张牌也要有不同 `card_id`。

## 2. 回合开始：缩盘、发牌、随机指向 [确定]

1. 只对当前存活者操作。保留其上一轮的环绕相对顺序；从幸存者列表起点依次重新编号。
2. 每个存活者**新增恰好一张**公开牌，其数值在 `[1,n]` 中独立、均匀随机抽取；没有实体有限牌堆，不限制牌值重复。
3. 未使用的旧牌保留，旧牌数值不因人数缩小而变化；允许牌值大于当前 `n`。
4. 对 `n` 个当前存活轮盘位置进行等概率随机，公开本轮初始目标。
5. 广播轮次、所有人的公开手牌、存活顺序、初始指向和决策期限。
6. 剩下 1 人时不进入下一轮、不再发牌。

**实现定义：**P2P 的对局协调/裁决机制在逻辑提交后只生成一次发牌和初始目标。所有界面只渲染最终确认结果；重发快照不得导致重新抽取。谁担任这个角色尚待 D-03a/e 决策。

## 3. 秘密同步行动 [确定]

- 本轮每名存活者仅可最终提交：
  - `PASS`：不出牌；不消耗任何牌。
  - `PLAY(card_id, PLUS)`：选自己当前仍持有的一张牌，位移为 `+value`。
  - `PLAY(card_id, MINUS)`：选自己当前仍持有的一张牌，位移为 `-value`。
- 提交前可在本地反复调整选牌、正负号或不出牌。
- 点击确认即锁定本轮行动，不能重复确认、换牌或撤回；其他玩家公开前只看得到「已有多少人确认」，看不到行动内容。
- **D-05 已确认：每轮决策时间为 15 秒**，从权威服务端进入 CHOOSING 开始计时。全部存活者的行动已经锁定（断线者按 D-06 自动 PASS）时可提前揭晓；否则服务端在截止时为未确认者补 `PASS`。客户端倒计时不决定动作是否被接受。
- 被淘汰玩家不能提交，但可以继续观看公共状态。

## 4. 统一公开与结果 [确定]

令当前轮盘玩家数为 `n`，初始目标的**0 基索引**为 `s`，全部锁定动作的带符号牌值总和为 `delta`，则最终 0 基索引为：

`target = ((s + delta) % n + n) % n`

> 双重模处理语言中负数余数，最终范围为 `0..n-1`。

- 公开的是完整动作列表，包括 PASS、打出哪张牌与正负方向。
- `target` 对应玩家**被命中并扣 1 点生命**；生命大于 0 继续参赛，生命归零才淘汰。**每轮命中一人，但不一定淘汰。**
- 本轮打出的牌先计入已出牌，之后将出局者仍持有的未出牌计入「淘汰弃」；不能重复消耗同一牌。
- 其他存活者手中未打的牌留到下一轮；**绝不继承出局者手牌**。
- 结算展示结束由**已选定的 P2P 对局协调/裁决机制**统一推进；任意玩家的本地动画、点击按钮不单独决定下一轮。
- 最后剩一人则广播胜利者，结束本局，不继续抽牌。

### 例子

剩 5 人，本轮起点为当前 4 号（0 基 `s=3`），行动合计 `+3-1=+2`，目标索引 `(3+2)%5=0`，即当前 1 号玩家命中、扣 1 生命；若归零则出局。

## 5. 手牌生命周期与统计不变量

每一张已发牌都始终且只处于其中一种状态：
- **HELD**：仍被一位存活玩家持有，未使用。
- **PLAYED**：已公开打出且消耗，归入「已出」。
- **ELIMINATED**：所属玩家淘汰时尚未使用，归入「淘汰弃」。

因此在**结算完成后**，整局和每种牌值均满足：

`issued = played + eliminated + held`

- 公开展示「已出」牌框可保留到本轮动画结束，但它已经不属于 HELD。
- 每一张牌必须持有唯一的 `card_id`，按 ID 迁移状态；不能只按数字删除。
- 不允许某一参与者上报未经验证的统计直接覆盖其他人的状态；统计来自最终一致的牌状态或经确认的裁决事件。
- 回合中展示的统计可附加阶段标识，避免把尚未揭晓的秘密打牌预先标为已出。

## 6. 边界情形验收

| 场景 | 正确结果 |
| --- | --- |
| 所有人 PASS | `delta=0`，初始目标扣 1 生命，生命归零才出局 |
| 正负位移互相抵消 | `delta=0`，初始目标同样扣 1 生命 |
| 旧牌 > 当前 `n` | 允许，位移按 `n` 循环 |
| 牌值为 `n` 倍数 | 最终位置不动，但确实打牌就消耗该牌 |
| 不同玩家同数字，或一人多张同数字 | 每张按 `card_id` 分别追踪 |
| 淘汰者本轮也出牌 | 出牌优先计入 PLAYED，其余 Held → ELIMINATED；无双重计数 |
| 只剩两人 | `+v` 和 `-v` 可能等价，**不附加特殊决斗规则** |
| 0 / 1 人 | 不允许建局/开始，或立刻结束；绝不除以 0 |
| 迟到/重复的确认和超时回调 | 不能重新出牌、重新发牌、二次淘汰或破坏统计 |
| 一人掉线 | 本轮已确认动作保留；未确认按 PASS；以后轮次仍保留席位并自动 PASS |

## 7. 规则层接口（拟定，不是已经存在的代码）

建议把纯规则写成不依赖 Node、场景、网络的模块，输入完整的可读逻辑状态与动作，输出**新的状态及结算事件**：
- `deal_round(state, rng) -> next_state + round_start_event`
- `validate_action(state, player_id, action) -> validation_result`
- `resolve_round(state, locked_actions) -> next_state + reveal_event + round_result_event`
- `is_match_over(state) -> bool`

> 这是接口语义草图，不要求按这些名字逐字创建函数。最终以代码评审通过的类型与测试契约为准。

规则逻辑既不启动计时，也不调用 RPC 或 UI；有助于自动测试和将来人机共用相同结算。

## 8. 用户已确认的房间与异常流程（2026-11-18）

- D-04：创建房间、凭房间码入房，至少 2 人且全部准备后房主才能开始；仍支持 2～12 名真人。
- D-05：**15 秒/轮**，全员确认提前公开，其他未确认者到期 PASS。
- D-06：开局前退出直接移除席位；比赛中断线保留席位及已确认行动，未确认和未来轮次 PASS，不立即淘汰。
- D-07：本局胜负结束回到原房间并重置准备，禁止进行中的比赛中途加入。
- D-08：人机补位 P1，不是本版规则实现的前置条件。
- D-03 最新方向：用户确认 **P2P**；房主权威还是 Mesh 一致性、NAT 穿透、保密与 Host 迁移仍待决。

本文件以前以 1 生命为默认，新增可调生命后的具体规则见 [初始生命规范](03-initial-lives.md)。规则与基本联网已实现最小 Demo，尚未满足完整公网 P0。

## 9. P2P 不改变数学规则（2026-11-18）

本节只区分规则与网络拓扑：每轮 15 秒、加减循环公式、明牌、资源保留、弃牌和胜负条件均保持。房主型 P2P 可能由 Host 在本地结算；全员 Mesh 则必须得到相同起点、锁定动作、淘汰和统计。由于房主也是真人玩家，其是否能读取对手的未公开动作属于**设计问题**，不能假定已经通过。Host 断线与 D-06 一般玩家掉线也需要不同应对。见 [P2P RFC](../02-architecture/03-p2p-architecture-options.md)。

## 10. 初始生命可调（2026-11-18 最新实施）

- **已新增 Demo 功能**：房主在开局前设置所有玩家相同初始生命，取整数 **1～5**，默认 1；具体范围属于本轮可调整的实现选择。
- 每轮确定最终目标后，该玩家生命 -1；**生命大于 0** 时不缩盘、不弃置他的未出牌，下一轮继续参加并获得一张新牌；**生命归零**才按此前规则淘汰、清空剩余手牌并缩盘。
- 生命值对所有客户端公开；只剩 1 人才产生胜者。默认 1 生命时恢复原来的一轮一淘汰行为。
- 因可能出现连续多轮无淘汰，旧版“12 人最多 11 回合、77 张累计发牌”的上界**只适用于初始生命=1**。详情与测试见 [03-initial-lives.md](03-initial-lives.md)。
